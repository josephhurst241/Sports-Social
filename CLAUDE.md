# CLAUDE.md

Sports Social (formerly Glass Motion, Prototype 6): the hub and three
baseline games (ping pong, bowling, golf). Laptop = host (3D scene), phone = motion controller over
WebRTC. Next.js 16 (App Router, Cache Components), React Three Fiber + drei, @react-three/rapier,
PeerJS, Zustand, Tailwind v4, TypeScript.

## Commands

- `npm run dev`: HTTPS dev server on the LAN (`scripts/dev.mjs` makes a self-signed cert for every local IP)
- `npm run play`: production build + server; measure performance here
- `npx tsc --noEmit`, `npx eslint .`: fast checks
- `npm test`: unit tests (`src/**/*.test.ts`, Node's built-in runner, which strips the types; import with the `.ts` extension)
- `node scripts/check.mjs --url=<url>`: headless end-to-end check (see README). Uses `window.__glass` from `Stage.tsx`

`SETUP.md` is the human setup guide (install, Windows, Supabase, Google, email codes, troubleshooting): update it when setup steps change.

## Conventions that bite

- **Telemetry**: one 9-float `Float32Array` (time, linear accel xyz, quaternion xyzw, grip) at 60 Hz on a negotiated `{ ordered: false, maxRetransmits: 0 }` channel. The PeerJS connection itself is `{ reliable: false }` (= ordered: false) and carries only control messages; PeerJS still retransmits on it, so it is not UDP-like, which is why telemetry has its own channel.
- **Telemetry never goes through setState.** It is copied into preallocated arrays and read in `useFrame` via `getState()`.
- **Quaternions are built on the phone** (`writeOrientationQuat`), already in three.js axes (+Y up, north = -Z). Never apply alpha/beta/gamma as Euler angles.
- **iOS motion permission** must be requested as the first statement of the tap handler, before any await.
- **Grip**: `onTouchStart`/`onTouchEnd` on the pane; `onTouchEnd` calls `preventDefault()` so the browser's imitation mouse events cannot re-grip; mouse events only for the desktop test pad.
- **Tone mapping is Khronos PBR Neutral.** The ground planes (the hub's at y = -0.5, `Floor` in the games) are `toneMapped={false}` so lit areas are exactly the background's #FFFFFF. The lights make them several times brighter than 1.0, so fog on its own stays clipped white and draws a hard line at the horizon: `Floor` clamps to white past the fog's near distance (not nearer, where glass samples it and needs the brightness), and spans 220 m so it reaches the fog.
- **Contrast between objects**: the studio environment is a bright white HDRI, so a glossy surface seen at a low angle mirrors white over its own color. Play surfaces (turf, lane) are matte with a low `envMapIntensity`; balls are solid and deep against them (bowling: each player's deep color in `BALL_COLORS`; ping pong: orange). Check new surfaces in a screenshot, not by their hex value.
- **Glass**: `Glass` (MeshTransmissionMaterial with `transmissionSampler`) for foreground objects, `BackgroundGlass` (native physical transmission) for island slabs. Both sample three's one shared transmission buffer, which only contains opaque objects: glass behind other glass is not refracted. Prototype 3's notes (fill rate, MSAA, tone mapping) apply if the hub grows.
- **Pointing**: the ray runs along the phone's top axis (hold it like a remote). It only aims while the phone is tipped toward the screen (`dir.y < 0.75`), so the upright rest pose never selects anything. Hover goes to the store only on change; selection on the grip's rising edge; a second tap on the selected island calls `enterGame`.
- **Working face**: the side of the phone that "faces forward". In ping pong it is the screen (+Z, held screen toward the table, like a bat); everywhere else the back (-Z, held screen toward you). Calibration (recenter) and `rig.heading` both use it, so a recenter in either pose agrees on which way the laptop is. The CPU's paddle packets carry the same half turn.
- **Arm models** (`rig.arm`): `pointer` (hub: phone = forearm from the elbow along its top edge), `paddle` (ping pong: hand swings around the shoulder by the phone's facing), `pendulum` (bowling, golf: arm hangs from the shoulder along the phone's bottom edge, putter continues along it). Phones report orientation, not position, so every model turns rotation into hand position.
- **Hold, swing, let go** (bowling, golf): power comes from the peak forward speed of the hand (bowling) or putter head (golf) in the last ~0.5 s (bowling) / 0.45 s (golf) before the grip is released; the phone's heading (`rig.heading`, where its back points) aims. Too gentle a release cancels instead of rolling.
- **Turns** (bowling, golf): two phones in when the game starts means two players taking turns, a frame each in bowling and a hole each in golf (`players`, `turn` in the store; `nextTurn` skips a player who left or has finished). Only `rigs[turn]` drives the ball. The host broadcasts `{ t: "turn" }` whenever `currentTurn()` changes, and the waiting phone shows whose turn it is instead of its buttons.
- **CPU telemetry** is written into slot 1 with `source = "local"`, so the avatar skips phone compass calibration for it.
- **Buttons mode** (`src/lib/input/buttons.ts`, the phone's default): the phone generates ideal motion packets from on-screen buttons, per scene, and sends `{ t: "input", mode: "buttons" }` so the laptop marks its telemetry `virtual` (no compass calibration, like the CPU). The laptop's games are unchanged by it; tune the recipes in `SWINGS` if a game's pace feels off.
- **Ping pong serve toss floats** (gravity x0.35 until hit) so a serve is about when you swing, not a 70 ms window.
- **Golf ball physics**: struck with matching topspin (no skid) and slowed by a constant turf deceleration (`ROLL_DECEL`) plus light damping. The cup is not a hole in the collider: when the ball's center crosses the rim (tested along its path since last frame, so a fast ball cannot skip it), `cupOutcome(speed, offset)` in `golf.ts` decides from how far the ball sinks while crossing the hole: a ball's depth or more drops, a little lips out (curls around the rim toward the cup's center side and loses speed), barely any hops over. Speed and line both count (dead center drops below ~1.9 m/s; `DROP_DEPTH` 0.85, `LIP_DEPTH` 0.3, forgiving). The `cup` phase plays it out on a kinematic path, then `holeOut()` (drop) or rolls on (`cupArmed` stays off until the ball is clear of the rim). Lip-outs and hops call out "Lipped out" / "Too fast" and wobble the flag. Tune with the constants next to `CUP_R`; `golfState.launch` rolls the ball for headless checks.
- **State machines advance once**: when a phase change triggers React state that only takes effect next frame (golf's next hole), switch to a holding phase first, or `useFrame` repeats the transition every frame.
- **Shadows**: one directional light with a fixed ±35 m box and a 2048 map covers the whole hub (about 3.4 cm per texel), so nothing clips.
- **Coordinates**: meters, +Y up, avatar faces -Z (away from the camera). Forward for yaw `f` is `(-sin f, 0, -cos f)`.
- **Color signatures**: `src/lib/game/theme.ts` maps each scene to a color. Stage's `Atmosphere` springs the fog (30-90 m, past the hub's islands) and a soft overhead spotlight to a pastel wash of it (`PASTEL`) with `@react-spring/three`, and `SkyDome` (follows the camera) is white overhead and takes the fog color at the horizon. Keep the sky's horizon tied to the fog: a fog color that differs from the sky draws a hard line where the fogged floor meets it.
- **UI theme**: `themeVars(scene)` puts `--accent` (signature), `--accent-ink` (its deep shade, ≥ 4.5:1 on white, `SCENE_INKS`) and `--wash` (the fog color) on each page's root; `globals.css` registers them with `@property` so the `themed` utility eases them in step with the fog. Tailwind sees them as `accent`, `accent-ink`, `wash`. Labels are `text-accent-ink`, values are ink. `panel` is the quiet surface (tinted toward the wash, opaque enough that the scene never shows through text); `panel-ink` is the inverse, kept for what is momentary or primary (callouts, the phone's main button). Text never sits bare on the 3D scene: give it a panel.
- **Glass looks**: `glassStyle` in the store, G on the laptop (remembered in localStorage). `Glass.tsx` holds both prop sets, "classic" (the prototype) and "liquid" (clearcoat, thicker lensing, more dispersion; the base to build the liquid-glass look on). Every prop is listed in both sets so switching back resets it. The liquid look is kept for later work; don't remove it.
- **Host page is dynamic**: it reads the LAN IP per request with `connection()` inside `<Suspense>` (route segment `dynamic` config is not allowed). `react-hooks/refs`, `immutability` and `set-state-in-effect` are off in `eslint.config.mjs`: they are React Compiler rules, and R3F code mutates scratch objects in the frame loop by design.
- **Startup animation** (`Splash`): pure CSS (`.splash` in globals.css) so it plays from first paint, not after hydration (in dev that is seconds late). `INTRO_SCRIPT` in `<head>` (layout.tsx) marks `<html data-intro>` before paint: `seen` (already played this session, hidden) or `skip` (a tap or key). The component only waits for the fade-out and clears `intro`; `CameraRig` holds the opening shot back by `INTRO_OFFSET` while `intro` is set and glides in after (`introGlide`: first load only). Never gate the room or scene on it.
- **Dev server not picking up an edit** (a stale CSS rule, say)? The project sits in OneDrive, and the file watcher can miss changes; restart `npm run dev`.
- **Accounts** (optional): with `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in `.env.local` (see `.env.example`), phones can sign in (Google, or a 6-digit email code that needs no redirect, so it works on any LAN IP); without them accounts are off and everyone is a guest. The phone sends `{ t: "profile" }` after connecting and on sign-in; the host keeps it as `players[slot].account`, and `playerName`/`usePlayerName` return it everywhere (chips, HUD, callouts). The host broadcasts `{ t: "names" }` for the waiting screen.
- **Room code vs. sign-in code**: both arrive as `?code=`. The Supabase client has `detectSessionInUrl: false`; only `/auth/callback` exchanges a sign-in code, then returns to `next` (local paths only).
- **Results**: at a game's end the host sends each player `{ t: "result" }` (`sendResult`); a signed-in phone saves it with `record_game()`, the only write path, which re-scores bowling from the rolls, checks golf cards and ping pong scores, and rate-limits. Self-reported: a player could forge their own games. Guests get a "Keep your scores?" prompt.
- **Motion calibration, per game** (`calibration.ts` rules, `calibrating.ts` runner, `CalibrationRunner` in Stage, `CalDiagram.tsx` drawings): the first time a Motion player enters a game (host.ts watches the scene), that game runs: a diagram of how to hold the phone, Ready, hold still 1.5 s (recenters; median heading = baseline; bumps `rig.neutralSeq` for the rest pose), then the game's action (putt / bowl with grip and release; ping pong a forehand, no grip) rep by rep until `repsDone` (3+ reps whose last three agree within 30%, or 6), each step waiting for Ready (`{ t: "calibrate-ready" }`). Result per player and game: `rig.games[game] = { swing, aimZero }` (`gameCal`: medians). `swing` multiplies bowling and golf power; `aimZero` (natural release direction from rest) is subtracted from `rig.heading` in Avatar while in that game. Settings' Calibrate re-runs the current game (not in the hub). Skip keeps the old result; leaving the game cancels a run; a phone leaving clears `rig.games`. The games ignore that player's grip while `calibration[slot]` is set; ping pong serves nothing while anyone calibrates. Buttons and the CPU are never calibrated.
- **Sensitivity**: the phone's Settings has Aim and Swing sliders (0.5x to 2x, Motion only), remembered on the phone and sent as `{ t: "sensitivity" }` on connecting and on change; the host keeps them as `rig.sens` (cleaned with `cleanSensitivity`). Aim scales the phone's yaw in Avatar; Swing multiplies bowling and golf power on top of calibration. Reset when the phone leaves.
- **Natural grip** (pendulum arm, bowling and golf): the arm is driven by how the phone has turned since its rest pose (`rig.neutralSeq`), not by its bottom edge, so any comfortable grip works: at rest the arm hangs straight down, swinging forward swings it, turning aims, and the hand (with putter or ball) turns by the same delta (`rig.handQuat`). The rest pose is taken whenever the scene places the player (each golf stroke, each bowling turn), on each new bowling ball, at calibration's swing step and on every recenter. Buttons and the CPU send an upright rest, as before.
- **3D hand**: the phone's own movement (accelerometer, a leaky integral) moves the hand in all three directions, up to 0.5 m, easing back to center; in ping pong, tipping the phone's top forward or back also lowers or raises the paddle hand (`PADDLE_LIFT`).
- **Aim assist** (`assistAim`, `AIM_PULL` 0.8): within a snap of the ideal line (golf: at the cup, 0.15 rad, about 8.5°; bowling: at the headpin, 0.032 rad) aim is drawn 80% of the way to it, continuous past the edge. Hub targets are sticky (the hovered island keeps the aim over a 1.75x sphere). Ping pong's near-miss reach is wider for people (`MAGNET_PLAYER` 0.4 m, `SWING_MIN_PLAYER` 0.5) than for the CPU.
- **Forgiving equipment**: paddle `BLADE_RADIUS` 0.13 m, bowling `BALL_R` 0.125 m, putter head 0.2 m wide; minimum swings `BOWL_MIN` 1.6, `PUTT_MIN` 0.25. Bowling draws its aim line from `aimFor`, the same function the release uses.
- **Focus camera**: when a player is lining up (bowling `holding`, golf `address`, ping pong serving, hub pointing at an island) the scene's `setView` eases in closer; `CameraRig`'s glide does the motion.
- **Split-screen ping pong** (`useSplit` in the store: always, in ping pong; against the CPU its half is the CPU's view): `SplitView` in PingPongScene takes over rendering (a frame callback with priority 1) and draws the scene twice. Both halves use `closeView`: close over the player's shoulder, following them along the baseline, closer while they serve. The shadow map is rendered once per frame. HostScreen draws the divider and name tags.
- **Make / miss**: games call `feedback("make" | "miss", x, y, z)` where the outcome is decided (golf in the cup / lip-out or hop; bowling strike or spare / a zero; ping pong a winner / net, out or a missed serve) and pass the same kind to `callout`. `Feedback.tsx` ripples rings from a fixed pool there (accent color for a make, grey for a miss); the callout pops or shakes (`.callout-make`, `.callout-miss`).
- **Settings**: the phone's gear (Controls, Calibrate motion, Aim and Swing sensitivity, Recenter, Haptics); the laptop's gear (sound effects on/off, glass look, calibrate a player). G still switches the glass.
- **Session stats** (`session.ts`): each player's games, wins and bests this session, in the laptop's memory only, updated in `sendResult`, shown on the player chips, wiped when that phone leaves or the slot is taken.
- **Logo sound**: `playChime()` plays only if the browser already allows sound (never queued to play late): at the splash's glint when allowed, or on the click or key that skips it. Off when the laptop's Sound effects setting is off (`sound` in the store, remembered in localStorage). There is no narrator or other voice audio.
- **Panel blur** is modest (`--blur-lg`; none on `panel-ink`): backdrop blur is redone over the moving canvas every frame and its cost grows with the radius. Measured: hub about 140 → 184 fps with that and a 256 px mirror floor.
- **Test pad extras**: `/play?sim=1&name=Ana` sends a display name (saves nothing), and the pad exposes `window.__phone` (store, account) like `window.__glass` on the laptop.
- **Frame rate looks capped at 30?** Chrome halves page frame rates on a Mac at low battery; the scene itself renders hundreds of fps uncapped.
